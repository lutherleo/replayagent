# Design decisions

Key design decisions in replayagent, each with the reasoning and what it would cost if it turned out wrong, in the format
`<decision> — <why> — <cost if wrong>`.

- workflows are plain synchronous functions replayed from the top; suspension is an internal `BaseException` — no asyncio, no generators, no stack snapshots, so workflow code reads like normal Python and replay is the only execution model — O(n) work per workflow task and O(n²) per workflow; a long-running workflow with thousands of steps would need a history cache / sticky execution (roadmap).
- SQLite (stdlib `sqlite3`, WAL, `synchronous=FULL` default) is the only store and the package has zero runtime dependencies — the target is a single node, and one transaction can append events, update the timer index, change status and consume an inbox row atomically — no multi-host deployment; a Postgres store would be a second implementation of `Store`.
- one writer per workflow, enforced by a compare-and-set on `(history_len, owner)` in every append — orders writes and fences a worker that lost its lease in one statement — a paused worker loses work it computed after the takeover (it is redone by the new owner, which is correct but wasteful).
- signals and cancellations go through an `inbox` table that only the lease holder moves into history — external writers never race the worker on `history_len`, and inbox consumption commits with the `SignalReceived` event (exactly-once into history) — signal latency is one worker tick (default poll 20 ms) instead of immediate.
- a dead lease owner on the same host is detected by PID (`host/pid/nonce` identity + `kill(pid, 0)`), other owners only by lease expiry (30 s default) — makes crash recovery immediate for the common single-machine case — PID reuse could make a dead owner look alive until its lease expires (only delays recovery, never double-runs, because of the CAS fence).
- activities default to at-least-once; an attempt interrupted by a crash is recorded as a failed `WorkerLost` attempt and retried immediately, counting toward `maximum_attempts` — matches Temporal semantics and bounds crash loops caused by the activity itself — non-idempotent effects can repeat; mitigated by the stable `idempotency_key` and the opt-in `at_most_once` delivery (fails with `ActivityOutcomeUnknown`).
- the idempotency key is `<workflow_id>/<cmd>`, not including the attempt — the same logical step must map to the same key across retries and processes — two different workflows reusing one external key space must include the workflow id (they do, by construction).
- determinism violations (`NonDeterminismError`, `VersionError`, swallowed suspension) park the workflow as `blocked` and never append a failure — the fix is a code deploy, and the history must stay replayable for that deploy — a blocked workflow needs an operator (`replayagent resume`); there is no automatic alerting.
- the replay check compares command type, activity name, SHA-256 of canonical-JSON arguments, timer duration, signal name/timeout, side-effect label and version change id, but not retry policies or timeouts — those are operational knobs people change on purpose; recorded options keep applying to scheduled activities — a change that only alters options is invisible to the checker (by design).
- `get_version` returns `DEFAULT_VERSION` without consuming a cursor position when history has another command there, and recorded markers the code no longer asks for are skipped — lets old executions replay the old branch and lets a `get_version` call be deleted after old executions drain (Temporal's model) — a marker-free history whose code later *removes* a guarded branch would still need a guard; documented in REPLAY_MODEL.md §7.
- `get_version` caches the decided version per change id for the whole execution and finds recorded markers by change id within the run of consecutive markers at the cursor (consuming them out of order if needed) — matches Temporal's per-changeID `GetVersion` contract, so one change can guard several sites without an in-flight execution mixing old and new branches, and deleting or reordering adjacent `get_version` calls no longer shifts another call onto the wrong branch — a history recorded by the pre-fix build that holds a second marker for the same id replays that marker as recorded (history wins over the cache), so such an execution keeps its recorded mixed branches until it drains.
- no non-blocking `handle.done()`; `wait_any` picks the handle resolved first *in history* — readiness "now" is timing-dependent and would break replay — workflows cannot poll; they must block on something.
- retry backoff (including jitter) is computed by the worker and recorded as `retry_at` — randomness outside workflow code is harmless if its result is recorded — a recorded `retry_at` cannot be changed for an already-failed attempt by editing the policy.
- activity timeouts fail the attempt in history but cannot stop the Python thread — threads cannot be killed safely in CPython; process-per-activity would add IPC and serialisation to every step — a hung activity leaks a pool thread until it returns; `activity_threads` caps the damage.
- cancellation is a hard stop (`CancelRequested` + `WorkflowCancelled` in one append), no in-workflow cleanup — keeps the replay model simple and compensation logic is out of scope — workflows needing cleanup must model it explicitly; roadmap item.
- crash injection is built into the engine as named crash points driven by `REPLAYAGENT_CRASH` (exit via `os._exit(77)`) or in-process `SimulatedCrash` — the engine must be tested by killing the process mid-workflow; named points make every gap between transactions testable deterministically, and a separate SIGKILL soak covers arbitrary moments — a few lines of test hooks ship in the runtime (no-ops unless the variable is set).
- the LLM layer is a provider-neutral `llm.chat` activity with Fake and Ollama providers, using only `urllib` — tests must be offline and deterministic; Ollama is the local model — no streaming responses; OpenAI/Anthropic providers are a small addition behind the same `LLMProvider` protocol.
- the research agent searches a bundled corpus of ten short documents written for this repo with an in-repo BM25 (k1=1.5, b=0.75), not the web — the demo and tests must be offline and reproducible — the agent's answers are only as good as ten paragraphs; it demonstrates the runtime, not research quality.
- golden histories (`tests/golden/research_v0.json`, `research_v1.json`) were recorded by `scripts/make_golden.py` at the commits before and after the citation check was added, and are committed — proves the versioning guard against a history the current code did not produce — regenerating v0 from today's code is impossible by design; if the history format changes, the goldens need a migration, not a re-record.
- coverage gate is 85% branch coverage over the whole package (measured 94.9%) rather than a per-module gate — the CLI/inspector formatting paths are less critical than the engine, which is at 94–98% — a regression concentrated in one engine module could hide behind the total; the coverage table is printed on every `make test`.
- the demo masks the machine name in printed worker identities (`<host>/pid/nonce`) — demo output is pasted into the README and must not carry personal machine names — none; the real identity is still used by the engine.
- `.python-version` pins 3.12 for local work and CI runs a 3.12 + 3.13 matrix — a fresh clone without the pin let uv pick 3.13, where unclosed `sqlite3` connections raise `ResourceWarning` (turned into errors by `filterwarnings = error`); every connection is now closed explicitly and the suite passes on both — 3.14 is untested.
